Sheet 1 — Overview & Key Principles

Sheet 1 of 7
Executive Summary
TL;DR for PM Lead and Tech Lead

✅ Good News: Low Decomposition Complexity

Table Tennis Singles is 1 server vs. 1 receiver per point. No multi-player decomposition required (unlike Football/Basketball). Most PT events map 1:1 to a Mamba action. This significantly reduces implementation risk.

⚠️ Watch: Notification Events vs. State Events

The feed emits ~50% scaffolding events (STP = State Position) that must be filtered — they carry no new scoring data. Additionally, GPOINT and MPOINT are notification duplicates of PT; do not double-count.

Sheet 4 — Event Decomposition Decision

Sheet 4 of 7

✅ Decision: 1:1 Mapping for Singles (No Decomposition Required)

Table Tennis Singles has exactly 1 player per side. Each PT event = 1 scoring action. No multi-player decomposition needed. This is the simplest case in WSC's sport portfolio.

Singles Pattern (current sample)

Provider PT event (seqNo=6)
  serverCompetitor: "200156" (KRIVOKAPIC)
  isWinner: "H"
  scoreH: 1, scoreA: 0
→ Mamba Action (1 action)
  ActionId: [next sequential]
  PlayerId: [200863 = SZABO] (winner)
  Period: G1, ScoreHome: 1, ScoreAway: 0

Doubles Pattern (future — not in sample)

Provider PT event (doubles)
  serverCompetitor: "TEAM_H"
  serverPlayer: "200863" (specific player)
  isWinner: "H"
→ Mamba Action (may need decomposition)
  Credit winning point to serverPlayer
  ⚠️ Doubles logic TBD — get sample

Player/athlete data arrives embedded inside competitor compositions. Path: unit[n].startList.start[n].competitor.composition.athlete[]. Each athlete object contains the full profile (name, DOB, nationality, gender).

→ code — WSC PlayerExternalId (ITTF player ID)

→ organization = "HUN" — IOC nationality code
→ gender = "M" — M / F
